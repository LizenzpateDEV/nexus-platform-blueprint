# ADR-0006: Application Structure

## Status

Accepted

## Kontext

Die langfristige Repository- und Projektstruktur muss vor Implementierungsbeginn feststehen, weil sie Paketgrenzen, Deployment und die Abbildung der Domänen (ADR-0005) bestimmt. Zwei Kandidaten stehen zur Bewertung:

**A – bisherige Empfehlung (Sprint-1-Plan): eine Produkt-App + Pakete**
```
apps/web/                     # eine Next.js-App
packages/platform/{8 Kernsysteme}
packages/modules/{Fach-Domänen}
packages/shared, ui, config
```

**B – vorgeschlagene Alternative: App-je-Bereich**
```
Nexus Platform
├── apps/
│   ├── erp
│   ├── crm
│   ├── docs
│   ├── hr
│   └── finance
├── packages/
│   ├── platform
│   ├── shared
│   ├── ui
│   └── config
```

Bewertungsrahmen: Die Struktur muss die Vision (Nexus Platform als Mehrprodukt-Basis, NPA-001) tragen, „Workspace First" (ADR-0004) respektieren, die Domänengrenzen (ADR-0005) umsetzen, für den KMU-Start schlank sein und den Weg zu Enterprise/White-Label (Phase 5) offenhalten.

### Bewertung der beiden Strukturen

| Kriterium | A – eine Produkt-App + Pakete | B – App-je-Bereich |
|---|---|---|
| Vision Mehrprodukt (NPA-001) | bildet nur das aktuelle Produkt ab | modelliert mehrere Apps – aber je **Domäne**, nicht je **Produkt** |
| Workspace First (ADR-0004) | erfüllt: Module komponieren in einem Workspace/einer App | verletzt: Module über Apps verteilt, kein einheitlicher Workspace |
| Domänengrenzen (ADR-0005) | über Paketgrenzen erzwungen | ebenfalls über Pakete – App-Zahl ist dafür irrelevant |
| Betrieb/CI (KMU-Start) | schlank, ein Deployment | mehrere Deployments, geteilte Auth/Session, Versionsabgleich |
| Unabhängige Releases | Module releasen gemeinsam | einzeln – nur nötig bei echten Einzelprodukten |
| White-Label (Phase 5) | über Tenant/Workspace-Branding | löst White-Label nicht; Branding bleibt Tenant/Workspace-Thema |

**Kernbefund:** Struktur B verwechselt **Produkt** mit **Domäne**. `crm`, `hr`, `finance`, `docs` sind laut Blueprint Fach-Domänen **innerhalb** des Produkts NexusERP AI (04_ERP_Modules, Roadmap-MVP), keine eigenständigen Produkte. Sie zu getrennten Apps zu machen, zersplittert ein zusammenhängendes Produkt: Ein Nutzer, der Sales bearbeitet, braucht CRM, Produkte und Rechnungen in **einem** Workspace/einer App – das widerspricht „Workspace First" unmittelbar. Zugleich ist Bs Verpackungsinstinkt (`platform/shared/ui/config` als Pakete, Apps an der Spitze) korrekt und deckt sich mit A.

Die richtige Achse für das App-Splitting ist das **Produkt / die deployte Erfahrung**, nicht die **Domäne**. Domänen sind Pakete; Produkte sind Apps.

## Entscheidung

Adoptiert wird eine **evolutionäre Hybridstruktur**, die den Verpackungsinstinkt von B mit der korrekten App-Granularität von A vereint:

1. **Fachlogik liegt in `packages/`** – Plattform-Domänen und Fach-Domänen als Bounded Contexts (ADR-0005). Hier leben die Grenzen; sie sind unabhängig von der Anzahl der Apps.
2. **`apps/` wird nach Produkt/Erfahrung geschnitten, nicht nach Domäne.** Aktuell existiert genau **eine** Produkt-App: `apps/web` (NexusERP AI), die die ERP-Domänenpakete komponiert.
3. **Governance-Regel:** Eine Domäne wird **erst dann** zu einer eigenen App, wenn sie zu einem eigenständig vermarkteten/gebrandeten Produkt mit eigenem Lebenszyklus, eigener Kundschaft oder eigener Deploy-Kadenz wird – **nicht** allein, weil sie eine eigene Domäne ist. Bis dahin bleibt sie ein Paket, das in die Produkt-App(s) komponiert wird.
4. **Ablehnung der wörtlichen Struktur B** (Apps je CRM/HR/Finance/Docs), da sie ein Produkt fragmentiert, „Workspace First" verletzt und den Betriebsaufwand vervielfacht. Ihr Paketierungsansatz wird übernommen.

### Zielstruktur (langfristig)

```
nexus/
├─ apps/
│  ├─ web/                 # NexusERP AI (aktuelles Produkt) – komponiert ERP-Domänenpakete
│  ├─ mobile/             # später: mobile Erfahrung (NPA-001 nennt Mobile Apps)
│  └─ <künftiges-produkt>/ # z. B. eigenständiges Produkt oder White-Label-Shell – erst bei echtem Bedarf
├─ packages/
│  ├─ platform/           # 8 Kernsysteme als Bounded Contexts
│  │  └─ identity, tenant, permission, data, module-engine, workflow, ai, integration
│  ├─ modules/            # Fach-Domänen als Bounded Contexts (ADR-0005)
│  │  └─ crm, sales, orders, billing, catalog, inventory, procurement,
│  │      finance, hr, projects, documents, reporting
│  ├─ shared/             # minimaler Shared Kernel
│  ├─ ui/                 # Design System
│  └─ config/             # Tooling-Presets
└─ (turbo.json, pnpm-workspace.yaml)
```

**Empfehlung in einem Satz:** Domänen als Pakete, Apps als Produkte; heute eine Produkt-App (`apps/web`), zusätzliche Apps ausschließlich für zusätzliche Produkte oder Erfahrungen (Mobile, White-Label-Shell) – die vorgeschlagene App-je-Bereich-Aufteilung wird nicht übernommen.

## Konsequenzen

**Positiv:**
- Trägt die Mehrprodukt-Vision, ohne verfrüht zu fragmentieren.
- Erhält „Workspace First": ein Workspace komponiert Module in einer App.
- Geringer Betriebsaufwand im KMU-Start; klare Regel, wann eine App entsteht.
- Grenzen auf Paketebene erzwungen – die App-Zahl ist davon entkoppelt.

**Kosten/Risiken:**
- Ein späterer Produkt-App-Split ist eine nicht triviale Migration. Deshalb müssen die Pakete von Anfang an echt entkoppelt sein – genau das leistet ADR-0005; die Grenzen jetzt sauber zu ziehen, hält einen späteren Split günstig.
- Das Team muss der Versuchung widerstehen, Domänen verfrüht zu Apps zu machen; die Governance-Regel adressiert das.

**Querschnittswirkung:**
- Baut auf ADR-0004 (Workspace komponiert Module → spricht für eine einheitliche App) und ADR-0005 (Grenzen auf Paketebene → App-Zahl orthogonal zu den Grenzen).

## Alternativen

- **App-je-Domäne (Struktur B wörtlich):** als primäres Langfristmodell verworfen – fragmentiert ein Produkt, verletzt „Workspace First", vervielfacht Betrieb, verwechselt Domäne mit Produkt. Der Paketierungsansatz (`platform/shared/ui/config`) wird übernommen.
- **Eine App + Pakete (Struktur A unverändert):** als **aktueller** Zustand adoptiert (ein Produkt = eine App), erweitert um die Regel, dass neue **Produkte** neue Apps werden.
- **Polyrepo (getrennte Repos je Domäne/Produkt):** verworfen – verliert atomare Änderungen über Plattform + Konsumenten, erschwert Versionsabgleich; Monorepo passt besser zu kleinem Team und eng gekoppelter Plattform.
- **Eine Next.js-App ohne Pakete (alles inline):** verworfen – keine erzwingbaren Grenzen, widerspricht ADR-0005 und Clean Architecture.
